Daily hospital files in. A warehouse you can trust out.

MediFlow is an Apache Airflow and PostgreSQL pipeline. It checks every row, keeps each patient's history, and proves that every load matches its source. The trace below is fourteen days of visits. Press replay and watch them load.

Every number on this page comes from a real run of the pipeline on synthetic data, so no real patient is involved. About 2% of the source rows are deliberately broken so the checks have something to catch.

What happens to one day of data

Seven Airflow tasks run in order. Each one handles a single batch date, so any task can be cleared and run again without doubling anything. Pick a step to see what it does and the code behind it.

    A star schema built for questions

    Facts record what happened. Dimensions describe who, where and when. Pick a question and the tables it needs light up, or click any table to see its columns and its real row count.

    Patients move. The history shouldn't disappear.

    When a patient changes city or insurance, the warehouse closes their old record and opens a new one (a slowly changing dimension, type 2). Every visit stays attached to the version that was true that day. Compare it with simply overwriting the old value.

    Bad rows are kept, not lost

    Every row passes 38 rules before it reaches the warehouse. A failing row is moved to a quarantine table together with the reason it failed, so the source team can fix it. Select a reason to see real examples.

    Run it twice, get the same warehouse

    A pipeline you cannot safely re-run is a pipeline you cannot trust. Every load here is an upsert guarded by the batch date, so repeating a day changes nothing, and a reconciliation step compares the warehouse with what was staged.

    Fingerprints before and after re-running three days

    An md5 over every row of each table, taken from the demo warehouse, then again after running Sep 5, 6 and 7 a second time.

    Reconciliation after every batch

      SQL for the heavy lifting, pandas for the rules

      Joins and history logic run inside PostgreSQL where they are set-based and fast. pandas only parses and validates one day's slice.

      Logic lives in a package, not in the DAG

      The DAG only decides when things run. The same code runs from the command line and under 47 automated tests, with or without Airflow.

      Older re-runs never overwrite newer data

      Upserts compare batch dates, and history rows are only closed when they started before the batch. Re-running last week cannot undo today.

      Dashboards never see patient names

      BI users get a role that reads only the mart schema, where patients appear as a token and an age band instead of a name and a date of birth.
