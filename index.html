03 / Reliability & governance

Make data problems
visible and traceable.

The README defines three quality outcomes and explicit recovery behavior. This is the project's control design—not a live monitoring feed.

↘

REJECT · Quarantine the row

Bad records are written to audit.rejected_rows with JSON and reasons, then excluded from the warehouse load.

Examples: null keys · negative fee · duplicate key
!

WARN · Keep with evidence

The row is loaded but the issue is recorded in the data-quality results, preserving visibility without discarding all usable data.

Examples: missing city · unknown diagnosis
×

FAIL · Stop the batch

Schema breaks and reconciliation mismatches fail the run. If the rejected ratio exceeds the configured limit, the batch fails after evidence is saved.

Default reject-ratio threshold: 20%
↻

Idempotent reruns

Staging reloads are batch-scoped and fact rows use natural-key upserts, so rerunning a date is designed not to create duplicate facts.

Safe rerun design
◷

Late-arriving lab results

A lab order first received as pending can be updated when its result arrives, completing the existing fact row instead of duplicating it.

Pending → Normal / High / Low
≋

Reconciliation & SCD2 checks

Compare staged and warehouse records by business key; verify one current patient version and no gaps or overlaps in history.

Mismatch → fail the run
◇
Privacy by design · BI access is intentionally narrow

The README describes a read-only bi_reader role limited to the mart schema. The reporting layer uses a pseudonymous patient token and age band rather than patient name or date of birth. All project data is synthetic.
